# Synthetic ID Generation

Back to [main plan](SPOTIFY_IMPLEMENTATION_PLAN.md#5-synthetic-id-generation)

## Problem

When the Response Parser processes a Spotify API response, it may encounter entities that don't yet exist in the database. For example, parsing an album response reveals tracks with artist references — those artists may not have been fetched yet.

In the staging layer, these records need to reference each other. For instance:
- A staged `track` record needs an `artist_id` for its primary artist
- A staged `entity_relation` record needs both `source_entity_id` and `target_entity_id`
- A staged `attribute_history` record needs `entity_id`

We cannot use real database IDs because the entities haven't been inserted into target tables yet. We need a synthetic ID system that:
1. Is deterministic — the same Spotify entity always gets the same synthetic ID
2. Is collision-free with real IDs
3. Allows resolution to real IDs during application

## Design

### Synthetic ID Space

Real database IDs are positive (generated by PostgreSQL sequences starting at 1). Synthetic IDs occupy the **negative space**:

```
Real IDs:      1, 2, 3, ..., Long.MAX_VALUE
Synthetic IDs: -1, -2, -3, ..., Long.MIN_VALUE
```

### Generation Function

```java
public class SyntheticIdGenerator {

    /**
     * Generates a deterministic synthetic ID from entity type + Spotify ID.
     * Uses a hash to distribute evenly across negative space.
     */
    public static long generate(SpotifyEntityType entityType, String spotifyId) {
        String key = entityType.getCode() + ":" + spotifyId;
        long hash = stableHash(key);
        // Map to negative space, avoid Long.MIN_VALUE (which has no positive counterpart)
        return -(Math.abs(hash) + 1);
    }

    private static long stableHash(String input) {
        // Use MurmurHash3 or similar stable hash (NOT Object.hashCode which varies across JVMs)
        return com.google.common.hash.Hashing.murmur3_128()
            .hashString(input, StandardCharsets.UTF_8)
            .asLong();
    }
}
```

Properties:
- **Deterministic**: Same (entityType, spotifyId) always produces the same synthetic ID
- **Stable across JVM restarts**: Uses MurmurHash3, not `Object.hashCode()`
- **Always negative**: Guaranteed non-collision with real positive IDs
- **Entity-type scoped**: Different entity types with same Spotify ID get different synthetic IDs

### Collision Risk

MurmurHash3 128-bit has negligible collision probability. Even with millions of entities, the chance of two different Spotify IDs hashing to the same synthetic ID is astronomically small (~10^-18 for 1M entities). If paranoia is warranted, we can add a collision detection step during staging writes.

## Resolution Process

During staging application, the Applicator resolves synthetic IDs to real IDs:

### Step 1: Build Resolution Map

```sql
-- For entities that were just inserted
SELECT spotify_id, id AS real_id FROM artist WHERE spotify_id IN (
    SELECT DISTINCT spotify_id FROM stg_artist_a WHERE status = 0
);
-- Plus newly inserted IDs from the RETURNING clause
```

### Step 2: Update Foreign Keys in Dependent Staging Tables

Before applying albums, resolve their `primary_artist_id`:

```sql
UPDATE stg_album_a stg
SET primary_artist_id = COALESCE(
    -- Try resolution table first
    (SELECT real_id FROM synthetic_id_resolution r
     WHERE r.entity_type = 'ARTIST'
       AND r.synthetic_id = stg.primary_artist_id),
    -- If not synthetic (already real), keep as-is
    stg.primary_artist_id
)
WHERE stg.primary_artist_id < 0;  -- Only resolve synthetic IDs (negative)
```

### Step 3: Handle Unresolvable References

If a staging record references an entity that hasn't been staged or doesn't exist in target tables, the Applicator has two options:

**Option A (Preferred): Defer** — Mark the record as `status=3 (DEFERRED)` and leave it for the next cycle. The referenced entity may arrive in the next staging window.

**Option B: Skip** — Mark as `status=4 (SKIPPED_UNRESOLVED)` and log a warning. The entity may need to be manually seeded.

### Resolution Table

```sql
CREATE TABLE synthetic_id_resolution (
    entity_type     SMALLINT NOT NULL,
    spotify_id      VARCHAR(64) NOT NULL,
    synthetic_id    BIGINT NOT NULL,
    real_id         BIGINT NOT NULL,
    resolved_at     TIMESTAMPTZ DEFAULT now(),
    PRIMARY KEY (entity_type, spotify_id)
);

CREATE INDEX idx_resolution_synthetic ON synthetic_id_resolution (synthetic_id);
```

This table persists across staging cycles, growing as new entities are created. It serves as a fast lookup for resolving synthetic IDs without querying the target entity tables every time.

## Alternative Considered: Spotify ID as FK

Instead of synthetic numeric IDs, we could use `spotify_id` (VARCHAR) as the foreign key in staging tables. This would eliminate the need for synthetic ID generation entirely.

**Pros**: Simpler, no hash function, no resolution step.

**Cons**:
- VARCHAR foreign keys are slower than BIGINT for joins
- Inconsistent with the rest of the system (all target tables use BIGINT PKs)
- Doesn't work for entity_relation and attribute_history which use generic (entity_type, entity_id) pairs — these need numeric IDs

**Verdict**: Use synthetic numeric IDs for consistency and performance. The resolution overhead is modest and happens once per staging cycle.
